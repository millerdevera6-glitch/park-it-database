# PostgreSQL Roles, Privileges, and Post-Restoration Access Control

## 1. Overview and Security Architecture

In the **BWIS Campus Canteen Pre-Order and Queue Management System**, security is enforced across two distinct architectural boundaries:
1. **Application-Level User Roles (Identity & Access Management):** Authenticated via JWT tokens and mapped in the Spring Boot backend (`SecurityConfig`).
2. **Database-Level PostgreSQL Roles & Privileges (Principle of Least Privilege):** Enforced within the PostgreSQL database cluster to prevent direct data tampering, SQL injection exploitation, and unauthorized access.

---

## 2. Distinction Between Application Roles and Database Roles

| Dimension | Application User Roles | PostgreSQL Database Roles |
|---|---|---|
| **Scope** | Evaluated within Java/Spring Boot runtime | Evaluated within PostgreSQL DBMS |
| **Identities** | `STUDENT`, `ADMIN`, `VENDOR`, Public (Unauthenticated) | `canteen_admin`, `canteen_app`, `canteen_readonly`, `canteen_app_grp`, `canteen_readonly_grp` |
| **Authentication** | BCrypt password hashes in `student` and `vendor` tables; JWT bearer tokens | PostgreSQL SCRAM-SHA-256 credentials via `pgpass.conf` or environment variables |
| **Database Connection** | End users **never** connect directly to PostgreSQL. All application requests flow through a single connection pool. | Used by Spring Boot DataSource (`canteen_app`) or DBA maintenance tasks (`canteen_admin`). |

---

## 3. PostgreSQL Database Roles Inventory

The project implements a **two-tier role architecture** separating login accounts from privilege-granting groups:

```
[canteen_admin]  --> Object Owner & DDL Migrations (LOGIN, CREATEROLE)
[canteen_app]    -- (Member of) --> [canteen_app_grp] (NOLOGIN, DML Privileges)
[canteen_readonly] -- (Member of) --> [canteen_readonly_grp] (NOLOGIN, Column-Limited SELECT)
```

### Role Specifications

| Role Name | Role Type | Attributes | Intended Operational Use |
|---|---|---|---|
| `canteen_admin` | Login Account | `LOGIN`, `CREATEROLE`, `NOCREATEDB`, `NOSUPERUSER` | Database object owner; runs migrations, DDL scripts, and administrative maintenance. |
| `canteen_app` | Login Account | `LOGIN`, `NOCREATEROLE`, `NOCREATEDB`, `NOSUPERUSER` | Runtime service account used by Spring Boot connection pool (`DB_USER`). |
| `canteen_readonly` | Login Account | `LOGIN`, `NOCREATEROLE`, `NOCREATEDB`, `NOSUPERUSER` | Read-only reporting analyst account for off-peak sales queries. |
| `canteen_app_grp` | Group (NOLOGIN) | `NOLOGIN`, `NOREPLICATION`, `NOBYPASSRLS` | Holds application runtime DML privileges across all 7 canteen tables and sequences. |
| `canteen_readonly_grp` | Group (NOLOGIN) | `NOLOGIN`, `NOREPLICATION`, `NOBYPASSRLS` | Holds column-level `SELECT` grants on reporting fields; excludes credentials and queues. |

## 5. Post-Restoration Access Control Findings & Vulnerability Analysis

During Activity 6 restoration testing into `canteendb_activity6_restore_test`, a critical PostgreSQL architectural behavior was observed:

### 1. Object-Level ACLs Were Preserved
The custom-format archive (`-Fc`) generated by `pg_dump` contains Table of Contents (TOC) entries for schema, table, and sequence access control lists (`ACL public TABLE ...`). Consequently, table-level grants (`canteen_app_grp` and `canteen_readonly_grp`) were successfully restored by `pg_restore`.

### 2. Database-Level CONNECT ACLs Were NOT Preserved (Security Finding)
- In the original database `canteendb`, `pg_database.datacl` was configured to restrict public access:
  ```sql
  datacl = {=Tc/postgres,postgres=CTc/postgres,canteen_app_grp=c/postgres,canteen_readonly_grp=c/postgres}
  ```
- In the restored database `canteendb_activity6_restore_test`, `pg_database.datacl` was `NULL`.
- **Reason:** `pg_dump` operates at the database level and does not dump database creation or database-level privileges stored in the global cluster catalog (`pg_database`).
- **Remediation Procedure:** Following any restoration, DBAs must re-execute `db-access-control/03-database-privileges.sql`:
  ```sql
  REVOKE ALL ON DATABASE canteendb_activity6_restore_test FROM PUBLIC;
  GRANT CONNECT ON DATABASE canteendb_activity6_restore_test TO canteen_admin, canteen_app, canteen_readonly;
  ```

### 3. Cluster-Wide Roles Must Be Provisioned Separately
Because PostgreSQL roles are cluster-wide, restoring onto a completely new server instance will fail if the roles `canteen_admin`, `canteen_app_grp`, `canteen_readonly_grp`, etc., do not exist. In a disaster recovery scenario, the DBA must run:
1. `db-access-control/01-create-roles.sql`
2. `db-access-control/02-role-memberships.sql`
before running `pg_restore`.
