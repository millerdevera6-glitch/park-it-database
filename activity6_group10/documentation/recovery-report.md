### 1. Incident Overview & Safety Guardrails

To validate disaster recovery procedures without endangering genuine production records, a controlled accidental data loss drill was conducted.
- **Safety Rule Compliance:** The live operational environment was completely untouched. The drill occurred strictly within the disposable restored test database (`boardtrack_db_activity6_restore_test`).
- **Disposable Test Record Strategy:** To preserve the integrity of genuine sample records (`properties`, `rooms`, `tenants`, `leases`, and historical `payments`), a dedicated, traceable disposable test record was introduced specifically for the simulation drill.
- **Foreign Key Dependency Check:** The test record was created in the `payment` table referencing existing `lease_id = 1`. Because child tables do not depend on `payment`, deleting this record tests real transactional recovery without triggering unintended foreign key cascade errors.

### 4. Comparison and Data Loss Analysis

#### 4.1 Comparison Results
- All baseline payments (IDs 1 through 6) were 100% restored with identical numeric amounts, foreign keys, and statuses.
- The recovery database successfully isolated the clean point-in-time snapshot without inheriting the accidental deletion incident.

#### 4.2 Critical Limitations of Logical Dump Recovery
While `pg_dump -Fc` provides reliable disaster recovery for static or periodically updated databases, the DBA must account for fundamental recovery boundaries:
1. **Discrete Point-In-Time Limitation:** A logical dump captures the database exclusively at the specific instant `pg_dump` runs.
2. **Post-Backup Transactions (The RPO Gap):** If an accidental deletion or data corruption occurs at 2:00 PM and the most recent backup was taken at 2:00 AM, **all transactional records inserted or modified during that 12-hour window are unrecoverable from the dump alone**.
3. **Data Loss Scenario Analysis:**
   - In our simulation, the test record (Payment #7) was inserted *after* the baseline dump was generated.
   - Consequently, restoring the baseline backup restores the system to its pre-incident health, but does not recover Payment #7.
   - **Production Remedy:** To eliminate data loss between daily dumps, production environments must implement **Continuous WAL Archiving and Point-In-Time Recovery (PITR)** by setting `wal_level = replica` and configuring `archive_mode = on` with `archive_command`. PITR allows the DBA to replay database transactions up to the exact millisecond immediately preceding the accidental `DELETE`.
