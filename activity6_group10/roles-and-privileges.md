### 1. Architectural Overview: Cluster-Wide Roles vs. Database Scopes

In PostgreSQL, user accounts, groups, and authentication credentials are **cluster-wide (global) catalog objects** stored in `pg_roles` and `pg_authid`. They exist outside the boundary of any single database.

#### The Single-Database Dump Boundary:
- A standard database backup generated by `pg_dump -Fc -d boardtrack_db` contains schema definitions, tables, views, triggers, and table data.
- **It does not contain role definitions.**
- If a database dump is restored into a new PostgreSQL cluster instance where the intended roles do not exist, object ownership mapping and access privilege grants (`GRANT ... TO ...`) will fail or default to the restoring administrator.
- Consequently, database administrators must maintain a separate, declarative role provisioning workflow to establish the access control foundation before running database restores.

### 2. Intended Access Control Model

Based on the official BoardTrack security specification in `docs/user-roles.md`:

```
+-----------------------------------------------------------------------------------+
|                                PostgreSQL Cluster                                 |
+-----------------------------------------------------------------------------------+
                                          |
                +-------------------------+-------------------------+
                |                                                   |
       [NOLOGIN Group Roles]                               [LOGIN Roles]
                |                                                   |
    +-----------+-----------+                     +-----------------+-----------------+
    |           |           |                     |                                   |
[boardtrack_ [app_      [app_                [boardtrack_owner]              [boardtrack_app]
 admin_grp]   runtime_   readonly_           (Database Owner &                (Node.js Runtime
              grp]       grp]                 Migration Runner)                System Account)
                ^                                                                     |
                |========================= Member Of =================================+
```

#### Detailed Role Definitions:

1. **`boardtrack_owner` (LOGIN Account):**
   - **Type:** Login-enabled user account.
   - **Purpose:** Serves as the database owner and executes structural schema migrations (`npm run db:migrate`).
   - **Permissions:** Owns `boardtrack_db`, the `public` schema, and all child objects.
   - **Security Restriction:** Strictly prohibited from being used by the Node.js runtime application for normal user transactions.

2. **`boardtrack_admin_grp` (NOLOGIN Group Role):**
   - **Type:** Non-login group role.
   - **Purpose:** Elevated administrative database management.
   - **Permissions:** Full Data Manipulation Language (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) on all business tables.
   - **Security Restriction:** Must **never** be granted `SUPERUSER`, `CREATEROLE`, or `CREATEDB`.

3. **`app_runtime_grp` (NOLOGIN Group Role):**
   - **Type:** Non-login group role representing the operational privilege envelope for the web application.
   - **Permissions:** 
     - `CONNECT` on `boardtrack_db`.
     - `USAGE` on schema `public`.
     - `SELECT`, `INSERT`, `UPDATE` on business tables (`property`, `room`, `tenant`, `lease`, `payment`, `utility_bill`).
     - `DELETE` permitted only on tables where business rules allow deletion.
     - `USAGE`, `SELECT` on all sequences (required for auto-incrementing PKs).
     - `SELECT` on views (`v_lease_summary`) and user authentication table (`app_user`).

4. **`app_readonly_grp` (NOLOGIN Group Role):**
   - **Type:** Non-login group role for reporting, business intelligence, and auditing.
   - **Permissions:** `CONNECT`, `USAGE` on `public`, and `SELECT`-only privileges across business tables and `v_lease_summary`. Prohibited from modifying data or executing DDL.

5. **`boardtrack_app` (LOGIN Account):**
   - **Type:** Login-enabled operational account utilized by the Node.js backend.
   - **Membership:** Belongs to `app_runtime_grp` (`IN ROLE app_runtime_grp`), thereby inheriting runtime permissions without having direct, unmanaged privilege assignments.
   - **Connection Limit:** Configured with a sensible ceiling (e.g., `CONNECTION LIMIT 25`) to prevent resource exhaustion.

### 3. Declarative Production Provisioning Script (`setup-roles.sql`)

The following SQL script recreates the complete role hierarchy, configures least-privilege grants, and sets appropriate schema ownership:

```sql
-- ============================================================================
-- BOARDTRACK PRODUCTION ROLE SETUP SCRIPT
-- ============================================================================
BEGIN;

-- 1. Create NOLOGIN Group Roles
CREATE ROLE boardtrack_admin_grp WITH NOLOGIN;
CREATE ROLE app_runtime_grp WITH NOLOGIN;
CREATE ROLE app_readonly_grp WITH NOLOGIN;

-- 2. Create LOGIN Accounts (Passwords supplied securely via environment or vault)
-- Replace '<STRONG_OWNER_PASSWORD>' and '<STRONG_APP_PASSWORD>' during deployment
CREATE ROLE boardtrack_owner WITH LOGIN PASSWORD '<STRONG_OWNER_PASSWORD>' NOSUPERUSER NOCREATEDB NOCREATEROLE;
CREATE ROLE boardtrack_app WITH LOGIN PASSWORD '<STRONG_APP_PASSWORD>' NOSUPERUSER NOCREATEDB NOCREATEROLE CONNECTION LIMIT 25;

-- 3. Assign Role Memberships
GRANT app_runtime_grp TO boardtrack_app;

-- 4. Database Connection Permissions
REVOKE ALL ON DATABASE boardtrack_db FROM PUBLIC;
GRANT CONNECT ON DATABASE boardtrack_db TO boardtrack_owner, boardtrack_admin_grp, app_runtime_grp, app_readonly_grp;

-- 5. Schema Ownership & Usage
ALTER SCHEMA public OWNER TO boardtrack_owner;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE, CREATE ON SCHEMA public TO boardtrack_owner;
GRANT USAGE ON SCHEMA public TO boardtrack_admin_grp, app_runtime_grp, app_readonly_grp;

-- 6. Table Privileges
-- Read-Only Reporting Group
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly_grp;

-- Application Runtime Group
GRANT SELECT, INSERT, UPDATE, DELETE ON 
    property, room, tenant, lease, payment, utility_bill 
TO app_runtime_grp;
GRANT SELECT ON app_user TO app_runtime_grp;
GRANT SELECT ON v_lease_summary TO app_runtime_grp;

-- Administrative Group
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO boardtrack_admin_grp;

-- 7. Sequence Privileges
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_runtime_grp, boardtrack_admin_grp;

-- 8. Configure Future Default Privileges (Ensures new tables inherit grants automatically)
ALTER DEFAULT PRIVILEGES FOR ROLE boardtrack_owner IN SCHEMA public
    GRANT SELECT ON TABLES TO app_readonly_grp;

ALTER DEFAULT PRIVILEGES FOR ROLE boardtrack_owner IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_runtime_grp;

ALTER DEFAULT PRIVILEGES FOR ROLE boardtrack_owner IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO app_runtime_grp;

COMMIT;
```

### 4. Privilege Verification and Audit Queries

To verify role attributes and grant assignments, execute the following audit queries:

#### 4.1 Audit Role Attributes
```sql
SELECT rolname, rolcanlogin, rolsuper, rolcreaterole, rolcreatedb, rolconnlimit
FROM pg_roles
WHERE rolname IN ('boardtrack_owner', 'boardtrack_admin_grp', 'app_runtime_grp', 'app_readonly_grp', 'boardtrack_app')
ORDER BY rolname;
```

#### 4.2 Audit Role Memberships
```sql
SELECT m.rolname AS member, g.rolname AS inherited_group
FROM pg_auth_members am
JOIN pg_roles m ON am.member = m.oid
JOIN pg_roles g ON am.roleid = g.oid
WHERE m.rolname = 'boardtrack_app';
```

#### 4.3 Audit Table Grants
```sql
SELECT grantee, table_name, privilege_type
FROM information_schema.role_table_grants
WHERE table_schema = 'public' 
  AND grantee IN ('app_runtime_grp', 'app_readonly_grp', 'boardtrack_admin_grp')
ORDER BY table_name, grantee, privilege_type;
```
